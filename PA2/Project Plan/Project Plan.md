1. # **Introduction**

   1. ## **Purpose**

   The purpose of this *Software Development Plan* is to detail all the necessary information in order to make an efficient plan for developing the product. Thís included defining clear scope for the product, setting out reasonable objectives to achieve, and aligning multiple stakeholder visions of said product.

    This document benefits not only the lead of the project \- by facilitating a plan and easing the need for monitoring \- but also individual members, by providing more transparency about the process and mitigating risk of misalignment.

   2. ## **Scope**

   This *Software Development Plan* details the plan for \<project-name\>, which includes but is not limited to the development process, the order of development, key objectives of the \<project-name\>, how the work is divided, what is the quality control process, etc.

   3. ## **Overview**

   This *Software Development Plan* contains the following information:

   Project Overview — detailing the goal of the project, what it set out to achieve, as well as the scope and limitation of said project. It will also clarify what will be the expected result of this development, and what assumptions will be made in said development.

   Project Organization — describes the organizational structure of the project team, which include information such as the role of each member, the responsibility of each member and team and the expected workload during the development.

   Project Plan — provides the comprehensive plan for the development process, details such as the estimated schedule, task assignments table and build plan will be provided in this section. 

2. # **Project Overview**

   1. ## **Project Purpose, Scope, and Objectives**

   Our project is a single-vendor e-commerce web application for an electronics store, aimed mainly at customers who are not familiar with technical specifications or only have a basic level of tech literacy. We aim to develop a software solution for the task of online shopping, not only just to simplify the process, but also to be a helpful assistant during that process.

   By the end of this project, we aim to deploy a fully functional web page, where customers can browse and search products, compare specifications, add items to a cart, check out, pay, and track their orders, and where store staff can manage products, stock, orders, promotions, and reviews. A key objective is our AI integration into the system, that recommends and compares products from everyday-language requests, helps with cart and checkout preparation, and answers order and stock questions, while the customer always confirms the order and payment.

   The system is a desktop web application for modern browsers (Chrome and Firefox), requires an internet connection, and delegates card and e-wallet payments to an external payment gateway.

The following assumptions are used to establish the initial project plan. These assumptions will be reviewed throughout the development process and updated if circumstances change.

### **2.2.2 Constraints**

The project must operate within the following academic, resource, technical, and organizational constraints.

| Constraint | Description |
| ----- | ----- |

4. # **Management Process**

   1. ## **Project Estimates**

   Given the limited timeline of this course, we have made the following estimation related to the timeline and resource:

* Software size: Our proposal includes 10 function groups with about 33 features in total (2–5 per group). The AI assistant, checkout and payment, and the admin side are expected to be the largest parts.   
* Effort: Works will be divided among 5 members (see Project Organization section). Assuming a fair division of task, it is estimated that each member needs to devote about 7.5 hours per sprint, or close to 40 hours throughout 5 the whole project. In total, roughly 200 hours, and this covers development, testing, documentation and meetings.  
* Time: The whole project’ timeline is controlled entirely by the course, so the date of our final build is expected to be delivered 11 weeks after the start of this project, or 9 weeks since the first proposal was sent.  
* Cost: Development costs are kept as low as possible.  
  * Backend and API: During development the backend runs locally on team members’ machines, at no hosting cost. Once the core features are stable, we plan to deploy it, most likely on AWS. The deployment cost is still \[TBD\] and will be estimated once the platform is confirmed.   
  * LLM API**:** The AI assistant uses an external LLM API with a budget of at most 1 USD per month.  
  * Email service**:** Password-reset and restock emails use a free tier, or a console/log output in development.  
  * Payment**:** Payments are tested through the gateway’s sandbox at no cost.

   4. ### *Configuration Management*

The team has four GitHub repositories: Frontend-SWE, Backend-SWE, docs-SWE and AI-SWE. Work is done on a separate branch and merged through a reviewed Pull Request. Do not push directly to main.  
Branch examples: feature/catalog-api, fix/login-validation, docs/project-plan. Commit example: feat: add catalog API. PRs should link to Jira and include test evidence.  
Documents use English Markdown, Mermaid diagrams where needed, and PDF for submission. Each section names its performer, reviewer and editor.  
Do not commit passwords, keys or .env files. Backend controls authentication and business data; AI accesses it through authorized APIs.  
If a build fails, the team checks logs, fixes or reverts the change, and tests again. Backup details are added when the server setup is finalized.
